# Decisions

This file records durable product and implementation defaults. New decisions should include their date, rationale, and conditions for reversal.

## 2026-11-24: agent-computer portability and synchronous exec design baseline

**Status:** accepted design baseline. It does not itself make a public support claim.

- **Use Go for control-plane changes and keep shell edits within existing installer/provisioning seams.** The existing control plane is Go (`go.mod` requires 1.23); no new dependency is needed. Reconsider only if an existing boundary cannot support the behavior without an unsafe or unmaintainable adaptation.
- **Capability-based preflight requires explicit `--allow-untested-host` or `CHASM_ALLOW_UNTESTED_HOST=1` for unqualified distributions; automatic package installation stays Debian-only via the optional Incus plugin.** Four distro trials demonstrate viable capabilities, but one trial is not a complete supported-distro matrix. Passing probes means prerequisites appear present, not that Chasm has qualified that distro. Never silently continue on an unknown distro. Reconsider the gate when a distro has repeatable install/upgrade/verify evidence and explicit package-manager ownership.
- **Resolve Incus as `INCUS_SOCKET`, the root-owned `/etc/chasm/incus-socket` setting, `/var/lib/incus/unix.socket`, then `/run/incus/unix.socket`.** Exact sudo helpers ignore the caller’s override and start with the installed setting. This matches the cross-distro evidence. An explicit override that is unusable is an error, not a silent fallback. Keep the systemd service environment strict to avoid caller-controlled remotes or ambient configuration. Reconsider only with evidence that supported Incus packaging requires another endpoint or environment variable.
- **Install root and system service executables in `/usr/local/sbin/`; keep operator CLIs in `/usr/local/bin/`.** Fedora 45's default policy leaves `/usr/local/libexec/chasm/chasm` as `usr_t` even after `restorecon` (2026-11-24 nested-VM qualification run on Fedora 45: installer run log and failure diagnostics). The service paths are `/usr/local/sbin/chasm-executor-server` and `chasm-supervisor-server`; `chasm` and `chasmctl` are regular files in `/usr/local/bin`. Keep `bin_t` verification on enforcing hosts after `restorecon`, and retain compatibility symlinks at both `/usr/local/lib/chasm/go/` and `/usr/local/libexec/chasm/` for upgrades. Do not add a custom SELinux policy. Reconsider only if a target distro's default `/usr/local/sbin` policy or live service trial disproves this choice.
- **Use sudo-rs-compatible sudoers tags for foreground exec.** Ubuntu 26.04's visudo rejects `NOLOG_INPUT` and `NOLOG_OUTPUT` (2026-11-24 nested-VM qualification run on Ubuntu 26.04: installer run log), so the exact `__exec` grant keeps `NOPASSWD` and `NOSETENV` only. Classic sudo with `log_output` or `use_pty` can change stdio; `runPrivilegedExec` in `cmd/chasm/exec.go` refuses non-FIFO stdin or stdout before reading the request. Reconsider the tag set only with a portable, tested syntax and equivalent fail-closed framing.
- **Use kernel hostname data and probe all four observed virtiofsd locations.** Avoid optional utility assumptions exposed by Arch; retain PATH and prior locations for existing hosts. Reconsider with new qualified package layouts.
- **Check host `incus-agent` prerequisite and enforce Go 1.23 minimum before builds.** Ubuntu 24.04 exposed both omissions. Report the missing host prerequisite directly. Reconsider the Go floor only with a deliberate module/toolchain compatibility change and tests.
- **Ship foreground synchronous `chasm exec` as unprivileged fixed-identity execution through an exact narrow sudo entry.** It complements `chasm shell` while retaining its same operator, host pin, sandbox name, site guest UID/GID, and no-root guest contract. Do not put long commands in the serial supervisor request loop. Detached sessions, file transfer, guest root, and remote execution require separate design and approval.
- **Pass argv directly; never invoke a host shell; do not inherit host environment; validate guest cwd/env and bound request/concurrency/output resources.** This keeps the new operation's input surface narrow. Reconsider only to add an individually reviewed, explicit capability with matching threat-model and audit updates.
- **Cancel/disconnect with TERM then bounded KILL; report unknown when completion cannot be proven and never retry automatically.** A possibly dispatched command may have side effects. Incus cancellation semantics must be qualified before shipping. Reconsider only with measured/verified behavior and an idempotency design.
- **Audit argv0, argument count, and a canonical full-argv SHA-256 digest.** The exec audit excludes argument tails, environment values, and stream payloads. Environment key names and phase timings may be recorded. A digest can reveal low-entropy commands by guessing. Incus retains its own operation metadata. Reconsider if audit requirements change, preserving content redaction by default.
- **Preserve confirmed guest statuses and use a separate structured status fd for certainty; helper codes 124/125/126 can collide with guest values.** POSIX exposes only 256 exit values, so disjoint representation of every 8-bit guest status plus control failure is impossible. A completed guest status of 0 with `output_code=output_incomplete` exits 125 so truncated output is never reported as process success; the status frame still reports `guest_status: 0`. Other confirmed guest statuses pass through. Callers needing certainty use the bounded JSON status frame on a caller-owned non-privileged fd. Reconsider only with a transport that carries status outside the process exit byte.
- **Use a bounded stdlib Incus local REST/WebSocket client for exec/control rather than infer guest status from the Incus CLI process code.** The CLI's process status conflates guest and transport outcomes. The REST result is structured, and cancellation uses the Incus exec control signal command (TERM then bounded KILL). No dependency is added. Reconsider if supported Incus versions lack the required local protocol or cancellation semantics; qualify before release.
- **Report Incus VM exec return 129 as unconfirmed.** Incus 6.0 can synthesize this return on VM disconnect. The structured result carries `incus_return: 129` without `guest_status` and the CLI exits 124. The native signal channel targets the primary command. Revisit when Incus exposes both an unambiguous VM terminal result and verified exit-by-signal metadata.
- **Make `chasm doctor --json` strictly read-only and consolidate observed checks/remedies.** It must not repair labels, run privileged mutations, start guests, or invoke installation. Use the exact zero-argument sudo helper for root-only reads and gate Incus GETs on a verified host identity and already-running service. JSON version 1 uses `ok`, `warn`, `fail`, and `skipped` statuses. Reconsider read-only behavior only through a separate explicitly named repair command with its own authorization and audit contract.
- **Record exec and CREATE/START/STOP phase timings in audit/observation, not by sampling or logging command data.** Use monotonic durations; lifecycle phases include clone, boot, guest-agent readiness, shutdown request, stopped confirmation, and total. Retain and expose observations through human and JSON `show`. Reconsider fields only additively once schema consumers exist.
- **Subsequent tranche candidates are stopped-only checkpoint/restore (root plus workspace, excluding `/shared`), opt-in shared access and peer traffic, loopback-first port forwarding, then optional stdio MCP after CLI contracts stabilize.** These address persistence recovery and isolation before agent-protocol breadth. They remain notes, not work authorization. Reorder if operator evidence identifies a more urgent user problem; any shared-volume default change needs an explicit migration decision.
- **No new dependencies, host Incus sudo access, systemd mutation from runtime commands, or installer execution from doctor.** Revisit dependencies only with a concrete capability gap and the required approval; keep host changes in the authorized installer/provision path.

### Open decisions

- **Unambiguous VM exec completion for return 129.** The goal remains to preserve every confirmed guest exit status. Incus 6.0 can synthesize 129 on disconnect, so the current implementation reports it as an unknown outcome. Revisit when an upstream mechanism or a qualified protocol can distinguish a guest exit of 129 from a transport loss.
- **Formal distribution support.** Promotion to the support matrix depends on operator-run installation, repeat provisioning, upgrade, and runtime trials. The capability gate and Debian-only package automation remain the current implementation defaults.
- **Initialized state for foreground exec and shell (L6).** The review found that a Running or Ready managed sandbox can accept a command before its `initialized` metadata becomes true. Keep the current behavior in this patch; decide whether both entry points should require initialization after the launcher and readiness contract is qualified.

These open items require qualification evidence before a policy change. The current conservative behavior needs no further approval.

### Reversal and qualification criteria

Revisit these defaults when a reproduced qualification run disproves a capability/path assumption, upgrade verification shows migration or label drift unsafe, Incus cancellation cannot bound orphan processes, users demonstrate that collisions between reserved helper codes and confirmed guest exit statuses block practical use, or a product decision changes identity, privilege, data sharing, supported distro claims, or public API. Preserve the rationale and evidence with any replacement decision.
